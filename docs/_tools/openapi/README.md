# OpenAPI generator for the REST API documentation

`generate.py` documents every REST operation of the backend that the hand-written spec in
`docs/source/api_docs` does not document yet. It reads the code, not a running server: the Flask app is built
without a database, once in cloud mode and once in on-premise mode, and every route is taken from its URL map.

```
python -I docs/_tools/openapi/generate.py --code-root <checkout> [--previous-root <checkout>] \
    [--spec-dir docs/source/api_docs] [--config docs/_tools/openapi/config.yaml] [--dry-run] [--report out.json]
```

- `--code-root`: the backend whose API is documented (the directory holding `cmdb/`). The interpreter running
  the script must have that backend's requirements installed and PyYAML (`--python` names another interpreter
  for the extraction if needed). Each code root and mode is imported in a child process.
- `--previous-root`: the previous release. Operations that do not exist there get `x-since` and the line
  "**New after 3.3.0:** ...". Update `SINCE_VALUE` / `SINCE_TEXT` at the top of the script for the next release.
- `--dry-run`: report only. `--report`: write every route, its metadata and the decision taken as JSON.

The 3.3.2 run was:

```
python -I docs/_tools/openapi/generate.py \
    --code-root <version-3.4.0 checkout> --previous-root <this repository at 3.3.0>
npx @redocly/cli lint --config docs/_tools/openapi/redocly.yaml docs/source/api_docs/openapi.yaml
```

## What it writes

- **New paths** go to `paths/<area>/<name>.yaml`. Every such file starts with
  `# generated by docs/_tools/openapi/generate.py - do not edit, re-run the generator`; a run deletes all files
  carrying that header first. They are listed in `openapi.yaml` between `# BEGIN GENERATED PATHS` and
  `# END GENERATED PATHS`; the hand-written entries above stay untouched.
- **New methods of a hand-written path** (mostly the `PATCH` that shares its code with a documented `PUT`) are
  appended to the hand-written file between `# BEGIN GENERATED OPERATIONS` and `# END GENERATED OPERATIONS`.
- **Tags** of new areas go between `# BEGIN GENERATED TAGS` and `# END GENERATED TAGS`.

A run replaces only these files and blocks, so it is idempotent: running it twice gives the same tree. To take
over a generated operation by hand, move it out of the markers (or the file out of the generated header), edit
it, and the next run will see it as documented.

## How an operation is derived

| Spec | Taken from |
|---|---|
| summary | first docstring line, made imperative ("HTTP `POST` route to mount ..." -> "Mount ..."), `Cmdb`/`Isms` prefixes dropped, plus the edition suffix |
| `[Cloud]` | the route exists in cloud mode, `verify_api_access` names `ApiLevel.ADMIN` (or `NO_API`) and the view has no on-premise-only guard (`if current_app.cloud_mode ...: abort(404)`) |
| `[OnPremise]` | the route exists on-premise and has no hosted-cloud-only guard (`if not is_hosted_cloud(): abort(404)`). On-premise `verify_api_access` checks no level, so `LOCKED` and `SUPER_ADMIN` routes are reachable with Basic auth and the right |
| description | `Required User Right: **<protect(right=...)>**`, the "New after 3.3.0" line, a note for LOCKED / SUPER_ADMIN, the docstring body, the `Raises:` section as **Errors** |
| path parameters | the Flask converters (`int` -> integer, `string`/`path` -> string), descriptions from the docstring `Args:` |
| query parameters | `parse_collection_parameters` -> the `CollectionParameters` component (as the hand-written files do); `parse_parameters(<class>)` -> the extra constructor arguments of that class; `request.args.get/getlist(...)` in the view and the REST helpers it calls (two levels) |
| request body | `validate(<schema>)` -> the Cerberus schema converted to JSON Schema (type, required, nullable, allowed -> enum, nested dict/list schema, min/max length, min/max, regex -> pattern, default); otherwise a `Validator(<schema>)` in a REST helper the view calls; otherwise the keys the view reads from `request.get_json()` (`payload.get(KEY)`, `payload[KEY]`, `KEY in payload`, also inside helpers the body is passed to); uploads (`request.files`, `get_file_in_request`, `request.form`, `get_element_from_data_request`) -> `multipart/form-data` |
| success response | the response classes the view uses: `GetSingleResponse` 200 `{result}`, `GetListResponse` 200 `{results}`, `GetMultiResponse` 200 (pager envelope), `InsertSingleResponse` 201 `{result_id, raw}`, `UpdateSingleResponse` 202 `{result}`, `UpdateMultiResponse` 202 `{results, failed}`, `DeleteSingleResponse` 202 `{raw}` / 204, `DefaultResponse` 200 (the value itself), file responses `application/octet-stream`. `result` uses the existing component schema only for `<area>` and `<area>/{id}` (`result_components` in `config.yaml`) |
| error responses | 401, 403, 500 always; 400 with input or when the docstring names it; 404 with a path parameter or when the docstring names it - all from `components/responses.yaml` |

Two Flask routes that differ only in the converter (`/media_file/<string:filename>` and
`/media_file/<int:public_id>`) share one OpenAPI path item; the parameter keeps its own type and says which name
the code uses.

## config.yaml

- `areas`: path prefix -> tag, directory and tag description (longest prefix wins)
- `exclude`: routes that are not documented, with the reason (see below)
- `result_components`: component schemas reused for `result` / `results` / `raw`
- `level_notes`: the sentence added for `LOCKED` and `SUPER_ADMIN` operations
- `overrides`: `"<METHOD> <path>"` -> `summary`, `description` (appended), `query` (replaces derived parameters
  of the same name), `requestBody` (replaces the derived one), `operationId`. Used where the code cannot be read
  mechanically - for example the section template routes, which take the template in the query string

## Excluded routes

| Route | Reason |
|---|---|
| `GET /` | Connection test of the frontend (infrastructure, no API level) |
| `GET /frontend_init` | Bootstrap data of the frontend (infrastructure, no API level) |
| `DELETE /setup/subscriptions`, `/setup/cache/user`, `/setup/cache/user/all` | Tenant setup of the cloud operator (`SUPER_ADMIN`, cloud only) |
| `POST /auth/login` | Token login of the frontend; the REST API authenticates every request with Basic auth |
| `/chatgpt/*` (2) | Backend of the frontend's ChatGPT helper in the DocAPI editor (`LOCKED`, no right) |
| `/start_assistant/*` (6) | Backend of the frontend's start assistant (onboarding wizard of an empty installation) |
| `/open_celium/*` (41) | Backend of the OpenCelium integration screens: forwards to the OpenCelium server; integrate with OpenCelium's own API instead |
| `GET /config_file/status/opencelium` | Tells the frontend whether the OpenCelium integration is configured |
| `/users/{user_id}/settings/*` (6) | Per-user preferences of the frontend (table layouts, views) |

A route that would be reachable on no documented channel (neither by the cloud API key nor on-premise) is
excluded automatically.

`SUPER_ADMIN` routes other than `/setup/*` (the user writes, the configuration import and reset) **are**
documented as `[OnPremise]`: in the cloud only the operator's key reaches them, but on a self-hosted
installation the REST API reaches them with Basic auth and the right, like any other route.

## The report

Every run prints:

- `EXCLUDED` - each excluded route and why
- `STALE` - operations the hand-written spec documents that no longer exist in the code. These are **not**
  removed automatically: delete the path item / file (and its `openapi.yaml` entry) by hand
- `EDITIONS` - hand-written operations whose `[Cloud]` / `[OnPremise]` suffix disagrees with the code
- `NO-DOCSTRING` - generated operations without a docstring (their summary is `<METHOD> <path>`)
- `NO-SCHEMA` - a `validate(...)` schema that could not be resolved (a generic object is written and the
  description says so)
